# ADR-0001：实时控制通道的选择

- 状态：**Proposed（建议，等待确认）**
- 日期：2026-10-01
- 分支：`dsh`
- 相关：[路线图](../roadmap.md)、[HCL 后端协议观察记录](../hcl-backend-protocol.md)、[实时门槛](../live-gate.md)

---

## 背景

项目目标是让 HCL 达到上游 `MCP-Packet-Tracer` 的功能等价，要求**实时控制并回读**。当前 61 项里只有 4 项实现，46 项标记为需要实时能力。

已有的实时证据全部来自 **Qt 窗口自动化**：遍历控件树、`InvokePattern`、`WM_SETTEXT`/`GETTEXT`、按滚动条与缩放投影设备中心、核对右键菜单特征。它确实成功过（打开/保存隔离副本、新增设备、增删链路），但代价与失败模式已经写满文档：

- 中权限下输入被拒（Windows 错误 5）；
- 锁屏时目标进程是 `LockApp`，必须停止输入；
- 画布平移导致固定像素命中注释，必须先做几何投影；
- 模态对话框改变 `MainWindowTitle`/`Handle`，旧 PID 与句柄不可复用；
- 每个新动作都要重新标定，成本随动作数线性增长。

同时存在一个硬阻塞：VirtualBox 6.0.14 与 Windows 11 build 26200 的 Hypervisor/VBS 冲突导致 guest 无法启动（`VERR_NEM_VM_CREATE_FAILED`）。项目把这个阻塞当成了**所有**实时能力的前置。

本轮只读调查发现两个事实（见[后端协议观察记录](../hcl-backend-protocol.md)）：

1. HCL 自带面向机器的后端协议（TCP `127.0.0.1:16600`），日志记录了 13 个动词的实际调用，覆盖建拓扑、建设备、分配控制台管道、电源、生命周期；仓库目前只用了 2 个只读查询。
2. 控制台是一个命名管道，名字由 `create_udp` 的应答返回（`\\.\pipe\<topo>-device<N>`），HCL 自己的 PuTTY 以**串口模式**打开它。CLI 的接入点是明确的，不需要模拟键盘。

---

## 决策驱动因素

| 因素 | 权重 | 说明 |
| --- | --- | --- |
| 可回读性 | 高 | 每个动作必须有与请求绑定的证据 |
| 与 guest 启动解耦 | 高 | 超分阻塞只应影响真正需要 guest 的能力 |
| 稳定性 | 高 | 不接受随画布平移/焦点/锁屏失效的控制面 |
| 厂商接口风险 | 中 | 后端协议未公开，可能随版本变化 |
| 使用者影响 | 中 | 不应打断使用者当前画布，不应改动源工程 |
| 实现成本 | 中 | 24 项 CLI 家族只有在通道稳定后才划算 |

---

## 考虑的选项

### A. 继续只用 Qt 窗口自动化
**优点**：不依赖未公开接口；已有原型与部分成功回执。
**缺点**：成本随动作数线性增长；对焦点、锁屏、窗口大小、画布平移敏感；无法为 24 项 CLI 家族提供稳定的文本回读通道。
**结论**：不足以支撑完整目标，只能作为"没有替代路径时的兜底"。

### B. 只做文件层（阶段工程），不做实时
**优点**：确定性、可测试、零厂商接口风险。
**缺点**：不满足"实时控制并回读"的目标；README 已明确"后端直接建设备不会自动更新当前画布"，文件与画布是两套真值。
**结论**：是必要的数据平面，但不是完整答案。

### C. 后端协议作为控制平面（+ 控制台管道）
**优点**：面向机器、行式请求/应答、天然可关联；`create_udp` 直接给出控制台管道；拓扑/设备/电源操作**不需要 guest 启动**。
**缺点**：未公开接口，存在版本风险；后端改拓扑不会刷新 GUI 画布（已记录），单独使用会造成双真值。
**结论**：采用，但必须与"让 HCL 载入工程"配合使用。

### D. Relay：文件写盘 → HCL 载入 → HCL 自行下发 → 保存回读
**优点**：真值唯一（HCL 进程内的拓扑）；除"打开/保存"外全部确定性；**该链路已被证明可行**（日志出现过 `NETFile::create_node`、`NETFile::add_connection`、双向 `create_udp` 成功）。
**缺点**：会重载使用者当前画布；仍保留一个窗口自动化动作。
**结论**：采用，作为拓扑变更的主路径，且只在隔离副本上操作。

### E. 在服务端内部实现结构化桌面控制（不使用 LLM 识图）
**优点**：理论上可覆盖 UI 独有动作（如"开启抓包"）。
**缺点**：仍然是窗口自动化，只是把脆弱性从 LLM 移到服务端；需要为每个动作建立并维护结构化定位。
**结论**：不作为主路径，仅保留给"后端与文件都没有等价动作"的极少数场景。

---

## 决策

**采用 D + C 的组合：**

1. **数据平面**：`.net` 文件与 `TopologyPlan`（已有实现，继续使用）。
2. **控制平面**：优先使用后端协议；拓扑变更走 relay（写盘 → HCL 载入 → HCL 自行下发 → 保存回读）。
3. **窗口自动化降级为单一窄动作**：只保留"让 HCL 打开/保存指定副本"，并继续使用已验证的隔离与回读保护。
4. **控制台 CLI**：通过 `create_udp` 应答返回的命名管道实现请求关联的会话，不模拟键盘。
5. **后端写动词默认关闭**，仅在 HCL 没有等价动作时启用，并落回执。

---

## 后果

**正面**

- 46 项"需要实时"中，约 19 项（D1）不再依赖 guest 启动，也不再依赖像素级自动化。
- 24 项 CLI 家族（D2）获得确定性的文本回读通道，具备了"逐条命令回读"的实现条件。
- 控制动作从"每个动作一套定位"变成"一套协议 + 一个窗口动作"，成本从线性降为常数。
- 超分阻塞的影响面从"全部实时能力"缩小到"guest 启动"。

**负面 / 风险**

| 风险 | 缓解 |
| --- | --- |
| 后端协议未公开，版本升级可能失效 | 动词白名单 + 版本探测 + 失败回执；只对 5.10.3 声明支持 |
| relay 会重载使用者画布 | 只在独立副本操作；默认不碰源工程；操作前后哈希回读 |
| 后端写入与 GUI 状态分歧 | 写动词默认关闭；拓扑变更一律经 HCL 载入 |
| 命名管道的并发/互斥行为未知 | 实现前先做只读测量；不允许抢占或任意宿主管道 |
| 使用未公开接口的合规与授权 | 本 ADR 状态为 Proposed，需用户确认后再实现 |

---

## 验证方式

1. **P2 只读阶段**：只增加可回读、无状态变化的动词，确认请求关联与失败归因。
2. **管道测量**：确认管道能否被第二客户端打开、是否有并发限制、是否原始终端字节流；该项不通过则 CLI 方案回到评审。
3. **relay 闭环**：一次写盘 → 载入 → 保存 → 回读，要求 `.net` 与 `query_topology` 一致、源工程哈希不变。
4. **不夸大**：命令被接受 ≠ guest 启动 ≠ 配置下发 ≠ 网络连通，四类结论分别取证。

## 待确认的开放问题

- 后端 `create`/`delete` 之后，GUI 是否存在"重新读取后端拓扑"的动作？若有，D1 的增量编辑可以完全绕开窗口自动化。
- `simware start` 是否就是"开电源"的正确动词？（仅观察 1 次且失败，属强推断）
- `set_hcl_tcp 18600` 打开的端口是否提供另一条更稳定的控制/控制台通道？
- 命名管道在 PuTTY 已连接时是否互斥？
